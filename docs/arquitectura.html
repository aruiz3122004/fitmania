Cómo está hecho FITMANIA

Sistema de gestión para un gimnasio de Barranquilla: venta de planes y productos, control de ingresos con pase QR, panel de administración, recepción con punto de venta, foro y PQRS. Este documento explica cómo está construido, cómo trata los datos de las personas y hasta dónde puede crecer sin rediseñarse.

¿Qué piezas hay y cómo se conectan?Vista general

Es un monolito modular: una sola aplicación Next.js sirve las páginas y la API. Firebase guarda los datos y autentica, y los servicios externos se llaman por HTTP desde el servidor. No hay servidores propios que mantener.

¿Cómo está estructurado el backend?Backend

Tres capas dentro del mismo despliegue. El borde (proxy.ts) filtra. Los route handlers autentican y validan. La lógica de negocio vive en lib/ como funciones puras o transaccionales que se prueban sin red.

Recorrido de una petición

  1. proxy.tsGenera el nonce de la CSP, rechaza un Origin ajeno en métodos que escriben y aplica el límite de peticiones. Si la ruta es un panel, exige la cookie de puerta firmada con HMAC.
  2. route handlerVerifica el token con verifyUserRequest o verifyAdminRequest (lib/auth-helpers.ts). Las cookies de sesión se comprueban con checkRevoked, así que cerrar sesión o quitar un rol tiene efecto inmediato.
  3. validaciónLos datos de entrada se validan y se normalizan en el servidor (lib/admin-validation.ts). Los precios, los días de plan y el stock siempre se leen de la base de datos, nunca del navegador.
  4. lib/La regla de negocio corre dentro de una transacción de Firestore cuando toca más de un documento: ingreso + estadística diaria, pago + plan + stock + orden, venta POS + inventario.
  5. auditoríaLas acciones sensibles escriben en audit_logs con actor, IP y diferencias antes/después (lib/audit-diff.ts). El cliente no puede escribir en esa colección.

¿Cómo se garantiza que no se cobre sin entregar?Pagos con Mercado Pago

El servidor fija el precio antes de cobrar y guarda una foto de la compra. Solo entrega cuando Mercado Pago confirma, y la entrega es una transacción idempotente: aunque lleguen cinco avisos del mismo pago, el plan se activa una vez.

  1. Socio → /api/payments/checkoutEnvía qué quiere comprar, nunca el monto. El servidor calcula el total con los precios de Firestore y crea payments/fm_<uuid> en estado pending, con productos, precios y días.
  2. Servidor → Mercado PagoCrea la preferencia con external_reference = la referencia propia. Si Mercado Pago no responde en 15 s, no se cobra nada y el carrito sigue intacto.
  3. Socio ↔ Checkout ProPaga con tarjeta, PSE, Efecty o saldo. FITMANIA nunca ve datos de tarjeta ni de cuenta.
  4. Mercado Pago → webhookSe verifica la firma x-signature (HMAC). Luego el servidor consulta el pago a la API de Mercado Pago: un aviso falso no puede aprobar nada.
  5. transitions.ts → fulfillment.tsDecide la transición (aprobado, rechazado, monto alterado, sobreventa) y, si corresponde, activa el plan, descuenta stock, crea la orden y avisa al admin en una sola transacción.
  6. Red de seguridadSi el aviso se pierde, el regreso a /pago/resultado consulta el pago, y el cron diario concilia los pendientes de más de 1 h. Un checkout abandonado vence a las 24 h.

Casos anómalos cubiertos

  • Monto distinto al calculado: queda en revisión, no entrega y alerta al admin.
  • Sobreventa: reembolso automático de lo faltante y alerta.
  • Pago tardío sobre un checkout vencido: se aprueba igual.

Por qué no hay SDK

Mercado Pago se consume por HTTP con fetch y tiempos límite. Son menos dependencias que auditar, y las respuestas se prueban con datos fijos en tests/mercadopago.test.mts.

¿Cómo se maneja la información del usuario?Datos del usuario

Solo se guarda lo que la persona hace a propósito: cuenta, compras, ingresos, foro, PQRS y autorizaciones. No se guarda historial de navegación. Cada colección tiene dueño, reglas de acceso y un plazo de conservación, y la persona puede descargar o borrar sus datos desde su perfil.

Lo que FITMANIA nunca tiene

  • Números de tarjeta, CVV o claves de PSE: quedan en Mercado Pago (PCI DSS).
  • Contraseñas: las maneja Firebase Auth.
  • Códigos MFA en claro: se guarda sha256 con sal y se borran al usarse.

Derechos del titular

  • Descargar: JSON con cuenta, compras, intentos de pago, ingresos, PQRS, foro y autorizaciones.
  • Eliminar: lib/account-deletion.ts borra perfil, MFA, publicaciones, comentarios y likes del foro y la cuenta de Auth, y anonimiza ingresos y PQRS. Las órdenes se conservan por obligación contable.
  • Consentimiento: versionado con LEGAL_VERSION.

Verificación en dos pasos por correo

Es opcional y sirve para socios, recepción y admin. Firebase solo ofrece SMS o TOTP, así que el factor por correo es propio. Se valida en cuatro lugares: la ventana global del cliente, cada ruta de API (isMfaSatisfied), los logins de los paneles y las reglas de Firestore (mfaOk()). Así, aunque alguien robe la contraseña y use el SDK directamente, no puede leer ni escribir datos.

¿Qué pasa si falla una capa de seguridad?Seguridad por capas

Ninguna protección depende de una sola capa. Si el cliente se salta la interfaz, lo detienen la API y las reglas. Si alguien encuentra la URL de un panel, lo detienen la puerta HMAC, la cookie de sesión y el rol.

¿Qué pasa si se cae el internet en la recepción?Recepción y plan B

La recepción sigue funcionando. El pase QR firmado se verifica con la llave pública sin red, los ingresos se encolan en el dispositivo y se envían al volver la conexión, sin duplicados. Si no hay equipo, existe una planilla en papel con el mismo formato.

Cola offline

Cada ingreso guarda un clientId único. Al sincronizar, el servidor ignora los repetidos. Riesgo: la cola vive en localStorage; si alguien borra los datos del navegador antes de sincronizar, esos ingresos se pierden. Hay que entrenar a recepción para no hacerlo y revisar el contador de pendientes.

Ingresos y estadísticas

El ingreso y su suma en daily_stats se escriben en la misma transacción. Los reportes leen agregados, no miles de registros.

Punto de venta

Efectivo, datáfono o transferencia. El stock se valida dentro de la transacción, así que no se puede vender lo que no hay. El cierre de caja queda en cash_closures.

PWA

El service worker cachea solo recursos estáticos. Nunca cachea /api, los paneles ni /pago, para que nadie vea datos viejos o ajenos.

¿Cómo escalará la aplicación?Escalabilidad

Para una sede la capacidad sobra. Vercel y Firestore escalan solos, y el trabajo caro (reportes, conciliación, avisos) ya está acotado. Los límites reales están en el costo por lectura, en la lista de usuarios del admin, que lee la colección completa, y en el cron que corre una vez al día con el plan gratuito.

¿Cómo se evita romper algo al cambiar el código?Calidad y CI

Cada push corre en GitHub Actions: tipos, pruebas unitarias, lint, pruebas de reglas en el emulador, build de producción y auditoría de dependencias. Si un paso falla, no se fusiona.

  1. tsc --noEmitTipos estrictos en todo el proyecto.
  2. npm test77 pruebas de lógica pura: transiciones de pago, cálculo de planes, pase QR, MFA, historial de compras, horario comercial.
  3. npm run lintESLint 9 con la configuración de Next 16. Hoy tiene 0 errores y 231 avisos, que son deuda de estilo.
  4. npm run test:rules16 pruebas de firestore.rules con el emulador (Java 21): perfil, plan, foto, MFA, órdenes, pagos, foro.
  5. next buildBuild de producción con variables de ejemplo.
  6. npm auditSin vulnerabilidades altas o críticas.

Además se hizo una prueba E2E del flujo MFA contra el servidor local (19 de 19), con un usuario temporal que se borró al final. No hay todavía pruebas E2E de navegador (Playwright) en CI. Es lo siguiente que conviene sumar, empezando por login, compra en sandbox y escaneo.

¿Por qué se eligió así?Decisiones de arquitectura

DecisiónAlternativa descartadaMotivo
Monolito Next.jsMicroserviciosUn equipo pequeño y una sede. Un solo despliegue, tipos compartidos, sin red interna que asegurar.
FirestorePostgreSQL gestionadoReglas por documento para lecturas directas del cliente, transacciones suficientes, sin servidor que operar. A cambio, los reportes usan agregados.
Solo Mercado PagoMercado Pago + StripeStripe no ofrece PSE ni Efecty en Colombia y duplicaba la lógica de entrega. Se retiró el 25-10-2026.
MFA por correo propioSMS de FirebaseTodos tienen correo, el SMS cuesta por mensaje y es vulnerable a SIM swapping. TOTP sigue disponible.
Pase QR Ed25519QR con el uidNo se puede falsificar ni reutilizar después de vencer, y se verifica sin internet.
Paneles en rutas ocultas con puerta HMACSubdominio aparteReduce la superficie visible sin otro despliegue. La seguridad real está en la sesión y el rol.
